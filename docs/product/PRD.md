# 走马村“认养一棵树”——认养履约与权益管理系统 PRD

> **系统定位**：面向认养用户、村民履约人员和运营人员，解决认养后履约过程不可见、权益兑现不稳定、村民协作依赖人工记录的问题，跑通一条可追踪的认养履约闭环。
> **核心原则**：先把认养履约做深，再扩展到乡村文旅交易和运营。不以功能数量证明产品价值，不把模拟结果或 AI 建议包装成真实业务效果。

---

## 1. 产品目标

### 1.1 核心目标

围绕一棵荔枝树建立从认养下单、养护任务、凭证审核到权益兑现和续养申请的可追踪闭环，让用户看见履约过程，让村民获得清晰任务，让运营人员能够处理异常和审核证据。

### 1.2 当前 MVP 范围

本阶段只验证 `LZ-018` 认养履约链路，核心用户和核心流程固定如下：

| 角色 | 核心任务 |
| --- | --- |
| 认养用户 | 查看树档案、选择认养方案、查看成长记录、申请权益和续养/退款 |
| 村民履约人员 | 接收养护任务、执行任务、上传凭证、响应退回和异常 |
| 运营人员 | 分配任务、审核凭证、处理异常、确认权益和结算门禁 |

核心流程为：`选树 → 认养下单 → 生成任务 → 村民接单 → 上传凭证 → 运营审核 → 权益兑现 → 续养/退款申请`。

### 1.3 非目标范围

以下能力保留在仓库中，但不属于当前 MVP 的主叙事或验收范围：

- 真实微信/支付宝扣款和自动退款；当前支付只保留演示入口，退款进入人工审核工单。
- 真实村民履约效率、运营收益或用户增长证明；固定种子模拟仅用于发现规则风险。
- 自动判责、自动结算和 Agent 直接修改订单、退款或履约状态。
- 门票、住宿、研学、空间改造、IoT、数字人、3D/AR、社区和 UGC。

### 1.4 关键成功指标

| 指标类别 | 具体指标 |
|----------|----------|
| **核心结果** | 到期权益按时兑现率 |
| **履约过程** | 任务按时提交率、凭证首次审核通过率、异常闭环时效 |
| **关系过程** | 成长记录查看率、收获权益使用率、续养意向率 |
| **护栏指标** | 退款处理时效、村民收益差异、人工介入次数 |

当前指标仅作为口径设计；真实基线和目标值需要在试点中采集，不把模拟数据当作真实业务结果。

### 1.5 参考范式

- **阿那亚**：目的地层 + 运营层 + 内容层 + 社群层的信息架构（借鉴平台结构，非视觉风格）
- **拈花湾**："内容介绍 → 库存选择 → 日期选择 → 立即订购"的交易路径

## 2. 用户画像与关键旅程

### 2.1 用户画像

| 用户画像 | 主要诉求 | 典型入口 | 成功动作 | 产品注意点 |
|----------|----------|----------|----------|------------|
| **认养用户** | 确认认养对象真实、持续看见成长、按约获得权益 | 荔田共生境、认养页、我的认养 | 认养下单、查看时间线、申请权益或续养 | 需要明确权益、履约状态和异常处理方式 |
| **村民履约人员** | 知道今天做什么、如何提交凭证、何时获得收益 | 村民任务页 | 接单、执行、上传凭证、处理退回 | 手机上步骤短，弱网和重复提交要有反馈 |
| **运营人员** | 统一分配任务、审核证据、识别风险并控制结算 | 运营后台 | 审核凭证、处理异常、确认权益和结算 | 高风险动作必须可追溯并保留人工确认 |

### 2.2 四条关键用户旅程

1. **认养用户**：`查看树档案 → 选择方案 → 提交认养 → 查看成长和任务进度 → 申请收获权益 → 续养或退款`。
2. **村民履约人员**：`接收任务 → 接单/开始执行 → 上传至少两张凭证 → 根据审核结果重提或上报异常 → 查看结算状态`。
3. **运营人员**：`生成或分配任务 → 查看凭证 → 通过/退回 → 处理延期、拒单和权益异常 → 确认结算门禁`。

### 4.2 交互主流程

```
首页/四境门户 → 看四境内容 → AI导览摘要/音频/云体验
                      ↓
              生成游览路线 ← 输入时长/人群/天气偏好
                      ↓
         高德路线 + 天气校验 + 模板匹配
                      ↓
              输出路线卡 + 推荐预约
                      ↓
    ┌───────────────┐
    ↓               ↓
认养荔枝树       扩展交易入口
    ↓               ↓
树档案与协议     门票/院落/活动
    ↓
养护任务与成长记录
    ↓
凭证审核 → 权益兑现 → 续养/退款工单
```

### 4.3 设计原则

1. **路线生成必须可解释**：不只是一张地图，必须同时显示总时长、步行强度、是否适合老人/儿童、雨天备选方案和需要提前预约的节点。
2. **认养页面必须有"仪式感 + 信任感"**：展示树档案、成长时间线、养护记录、权益说明和收获兑现方式。
3. **后台与村民协作端必须尽量"低培训成本"**：考虑实际居住人口有限、老龄化较明显、运营主体不足的现实。

## 5. 技术架构

### 5.1 技术栈

| 层级 | 技术选择 | 说明 |
|------|----------|------|
| **应用** | Next.js 14、React 18、TypeScript | `apps/web` 用户与村民端，`apps/admin` 运营端 |
| **HTTP 边界** | Next.js Route Handlers / Admin BFF | `/api/v1` 承载服务端接口，Admin 通过同源 BFF 访问 |
| **数据** | Prisma、PostgreSQL、Redis | 领域记录、迁移、种子数据、缓存和幂等支持 |
| **知识** | 本地 BM25、角色过滤、PII 清洗 | 草案知识、逐字引用和安全拒答 |
| **规则评测** | 确定性 V0/V1 模拟 | 固定种子、场景、指标、事件和 Bad Case |
| **地图与界面** | Leaflet、next-intl、Tailwind CSS | 地图展示、三语言资源和响应式界面 |
| **模型调用** | ModelProviderAdapter / DeepSeek | 服务端调用；无密钥或失败时使用受控降级 |
| **支付** | 演示状态 | 尚未接入真实微信或支付宝通道 |

### 5.2 模型层策略

当前 `ModelProviderAdapter` 只在服务端配置 `DEEPSEEK_API_KEY` 时调用 DeepSeek；没有密钥、请求失败或超时时返回固定降级结果。模型不承担认养状态机、退款、判责或结算。

知识问答优先使用本地 BM25 检索和角色过滤；履约协调 Agent 处于影子模式，只能读取必要信息并生成建议。知识源仍为 `draft` 时不可用于生产召回。

## 6. 权限模型

推荐至少分为八类角色（RBAC）：

| 角色 | 权限范围 |
|------|----------|
| 游客 | 浏览公开内容、生成路线、查看天气 |
| 注册用户 | 预约、购票、认养、反馈、查看个人订单 |
| 认养用户 | 注册用户权限 + 查看树档案、养护记录、参与养护活动 |
| 房东/院落协作者 | 管理房源库存、更新入住状态 |
| 内容编辑 | 管理四境内容、场景页配置 |
| 客服运营 | 处理反馈工单、查看订单 |
| 财务/订单管理员 | 订单管理、退款操作、对账 |
| 系统管理员 | 全局配置、权限管理、审计日志查看 |

**审计要求**：当前对树档案修改、退款工单、权益、结算和删除用户数据保留审计关联；真实支付接入后，支付回调、对账和退款操作也必须进入审计日志。

## 7. 隐私与合规

1. AI 导览、反馈总结、翻译、路线解释等场景，优先发送**脱敏后的结构化片段**，不把手机号、精确地理位置、未脱敏订单文本直接送到境外模型。
2. 公开用户问答场景，优先采用**国内模型网关**或最小化数据出境方案。
3. OpenAI API 默认生成最长 30 天的 abuse monitoring logs，`store=false` 不等于零保留。
4. 需同时考虑《生成式人工智能服务管理暂行办法》《个人信息保护法》《网络安全法》的边界。
5. **以上只构成产品设计建议，不替代专项法律意见。**

### 8.3 月度运营成本

**成本控制要点**：
- 高频路线生成和反馈总结尽量使用 mini 或国产模型
- 避免每个用户请求都触发联网搜索
- 天气、路线模板、常见导览问答都应做缓存与复用

## 9. 后续演进

| 阶段 | 重点 | 内容 |
|------|------|------|
| **第一阶段** | 跑通闭环 | 首访转化 + 认养复访，让系统变成经营工具 |
| **第二阶段** | 增强体验 | 360 内容、轻 AR、数字讲解员、研学互动脚本、多语言 |
| **第三阶段** | 智能升级 | 生态感知、数字孪生、动态定价、果园传感器、策略推荐 |

**核心理念**：先把真实资源组织好，再把数字能力叠上去。避免"系统很复杂，但村庄没有真正因为它而更好运营"的常见失败路径。

---

> **总判断**：这个项目最优解不是"做一个乡村版阿那亚 App"，而是"做一个以走马村真实资源为核心、以轻平台和 AIGC 运营为手段、能把四境内容、预约交易、认养关系和日常复盘连成闭环的乡村操作系统"。
