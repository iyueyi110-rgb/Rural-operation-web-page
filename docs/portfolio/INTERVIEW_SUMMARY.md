# 面试版项目摘要

## 一句话定位

面向认养用户、村民履约人员和运营人员，解决认养后养护过程不可见、权益兑现不稳定、村民协作依赖人工记录的问题，先用 `LZ-018` 跑通一条可追踪的认养履约闭环。

## 为什么做这个项目

一线沟通共 12 人次，覆盖村书记和村民；12 是沟通人次，不是去重用户数。现有证据支持把“长期履约是否可信”作为优先问题，但还不能证明真实购买意愿、履约效率或商业收益。

在门票、住宿、研学和认养等候选方向中，认养能把树档案、任务、凭证、权益、结算和续养串到同一个业务对象上，因此更适合验证长期关系，而不是一次性浏览或交易。

## 核心方案

`选树 → 认养下单 → 生成任务 → 村民接单 → 上传凭证 → 运营审核 → 权益兑现 → 续养/退款申请`

三类角色围绕同一条履约记录协作：

- 用户看到树档案、成长记录、权益和异常处理结果。
- 村民看到明确任务、截止时间、凭证要求和结算状态。
- 运营审核凭证、处理延期与拒单，并控制权益和结算门禁。

## 个人贡献表述

以下口径用于产品经理面试，使用时应与个人真实参与范围保持一致：

1. 从多业务方向中收敛认养履约 MVP，定义三类用户、主流程、非目标和 `LZ-018` 黄金案例。
2. 设计任务、双图凭证、退回重提、权益、结算和退款工单的完整状态边界，并补齐异常矩阵。
3. 建立以到期权益按时兑现率为北极星的指标树，设计 10 至 20 棵树的最小真实试点。
4. 用固定种子成对模拟评估规则，发现效率、质量和公平性之间的冲突，并据此暂缓 V1 升级。
5. 将产品文档、代码事实、Demo 路径、测试和降级说明整理为可复现的招聘证据链。

## 关键取舍

| 决策       | 选择           | 原因                                                         |
| ---------- | -------------- | ------------------------------------------------------------ |
| MVP 范围   | 只突出认养履约 | 先验证一个长期服务闭环，门票和住宿降级为扩展能力             |
| 高风险动作 | 人工审核       | 退款、判责、权益和结算影响真实利益，不能由未验证规则自动推进 |
| Agent      | 只读影子建议   | 当前没有足够真实模型建议，不具备自动执行依据                 |
| 支付       | 保留待支付状态 | 尚未完成资质、回调、对账和退款责任链路                       |
| 规则升级   | 40 组均暂缓    | 过程效率改善不足以覆盖验收率、公平性和审核容量风险           |

## 可展示证据

- `LZ-018` 七步 Demo 串联用户端、村民端和运营端。
- Web 自动化测试覆盖认养状态、鉴权、上传约束、降级和演示契约。
- 5 个固定种子 × 8 个场景，共 40 组 V0/V1 同世界成对模拟。
- 13 项模拟指标保留分子、分母、定义和事件追溯。
- 固定知识评测中可回答问题召回 20/20，运营专属内容泄漏为 0。

> 模拟运营数据，不代表真实业务结果。以上结果不能证明真实转化率、村民效率、平台收益或因果效果。

## 主动说明的限制

- 没有真实支付、自动退款、自动判责或真实资金结算。
- 退款只创建人工审核工单。
- Agent 不直接修改订单、任务、权益或结算。
- 真实指标基线、价格接受度和单位经济性仍需试点建立。
- 调研原始记录涉及个人信息，公开仓库只保留方法、结论和边界。

## 下一步

在一片果园选择 10 至 20 棵树，邀请少量认养用户、3 至 5 位村民和 1 至 2 位运营人员，至少运行 30 天并覆盖一次权益兑现。重点验证到期权益按时兑现、任务与凭证质量、村民收益差异、异常成本和续养意向。

- 推动 `LZ-018` 黄金案例落地为可复现 Demo，串联任务、双图凭证、人工审核、权益、结算门禁和售后工单。
