# 3 分钟 Demo 演示脚本

本脚本只演示 `LZ-018` 认养履约闭环。门票、住宿、研学、空间改造、IoT 和数字人不进入主演示。

> 页面中的业务记录为演示数据；模拟运营数据，不代表真实业务结果。真实支付、自动退款、自动判责和自动结算均未接入。

## 演示前准备

```bash
.\start.cmd
```

`start.cmd` 会准备本地演示环境并启动 Web/Admin；若数据库不可用，可改用 `pnpm --filter @zouma/web dev` 打开只读降级路径。

打开：

- 用户端：`http://localhost:3000/zh-CN/demo`
- 运营端：`http://localhost:3001/tasks`

本地演示身份：

- 认养用户：点击用户端的“一键演示登录”，无需手机号。
- 村民：手机号 `13800000011`；短信服务不可用时使用页面返回的开发验证码，固定值为 `888888`。
- 运营管理员：访客可只读浏览；本地启动脚本配置演示环境后，写操作口令为 `zouma-demo-local`。

若页面显示“只读降级导览”，继续按相同顺序讲解页面和产品边界，不执行写操作，也不口述为已经成功下单、上传、审核或结算。

## 时间分配

| 时间      | 页面与动作                                  | 必须讲清的产品判断                                                                |
| --------- | ------------------------------------------- | --------------------------------------------------------------------------------- |
| 0:00–0:25 | 打开 `/zh-CN/demo`，确认演示模式和 `LZ-018` | 本项目只验证一条认养履约闭环，三类角色共用同一业务对象                            |
| 0:25–0:50 | 打开 `LZ-018` 树档案，查看一年期方案        | 用户购买的不是一棵树的所有权，而是可持续查看的养护过程和约定权益                  |
| 0:50–1:15 | 进入待支付演示状态                          | 未接入真实微信或支付宝扣款，不把待支付状态描述为真实成交                          |
| 1:15–1:40 | 村民 OTP 登录，查看并接取养护任务           | 任务明确截止时间、48 元演示收益和至少两张凭证要求；收益为规则样本，不是实测收入   |
| 1:40–2:05 | 村民提交两张凭证                            | 图片不足、上传失败和任务版本冲突都必须显示失败，不伪造提交成功                    |
| 2:05–2:30 | 切换运营任务台，先退回再复核通过            | 黄金案例保留两版凭证；人工审核是权益和结算的门禁                                  |
| 2:30–2:45 | 展示权益、结算和续养节点                    | 退款只创建人工审核工单；自动退款、自动判责和自动结算不在当前 MVP                  |
| 2:45–3:00 | 打开 `/simulations` 的 Bad Case             | 用连续降雨或权益延迟说明规则缺口；40 组模拟不能证明真实业务收益，也不支持直接升级 |

## 异常时的标准说法

- 数据库不可用：当前为只读降级路径，树档案可浏览，但写入能力不宣称成功。
- 上传失败或不足两张：保留在当前任务，不进入待审核。
- 审核退回：生成新凭证版本，旧版本不覆盖，便于复盘责任和处理时效。
- 村民拒单或超时：进入运营改派或人工跟进，不自动判定村民责任。
- 连续降雨：允许延期并保留原因，最终时限和补偿需运营确认。
- 支付未接入：只展示待支付演示状态，不产生真实扣款。
- Agent 无模型密钥：显示明确降级；Agent 只提供影子建议，不直接修改订单、任务、权益或结算。

## 面试收尾

一句话总结：我没有把乡村文旅做成大而全的平台，而是先用 `LZ-018` 跑通“用户看得见、村民做得清、运营审得过”的履约闭环，再用真实试点验证按时兑现率、履约成本和续养意向。
